# Research 2026-11-13: options for a reliable HDMI video looper

Historical survey from the start of the project, kept as written apart from
wording. It led to the ESP32-P4 player in this repository; the single-board
computer (Orange Pi) arm it mentions is not part of this repository.

## Problem
Cheap USB-stick HDMI media players fail at looping one video unattended.
Typical failure modes:
- Black frame or stutter at the loop point: the player reopens the file each
  time. Content issues make it worse (first frame not a keyframe, open GOP,
  MP4 edit lists, AAC priming, audio/video length mismatch).
- No recovery after a power cut, or the device does not autoplay.
- HDMI hot-plug: display powered after the player → no output or wrong mode.
- Codec beyond the box's hardware decoder (HEVC 10-bit, 4K60) → stutter.
- File system: exFAT/NTFS unsupported, macOS `._*` files picked up as media.

Mitigations for existing boxes (kept for reference): FAT32/MBR stick, single
file in root, `dot_clean -m`, H.264 High@4.1 1080p30 CFR yuv420p + AAC-LC,
faststart, and concatenating the clip many times so the seam is rare.

## ESP32-P4
- No H.264 hardware decoder (encoder only, 1080p30). Software H.264 decode:
  1280×720 @ ~10 fps (Espressif). The ESP-HDMI-Bridge project claims "H.264
  from microSD up to 1080p60" without saying how; it conflicts with
  Espressif's numbers and with the BSP's 1080p30 HDMI ceiling — treat as
  unverified.
- Hardware JPEG decoder: 1920×1080 YUV422 → RGB ~48 fps; 1280×720 ~109 fps
  (ESP-IDF docs, 360 MHz CPU, 200 MHz PSRAM, JPEG-only benchmark). Output is
  1088 lines.
- HDMI via LT8912B (MIPI-DSI → HDMI). Espressif BSP modes: 800×600@60,
  1280×720@60, 1280×800@60, 1920×1080@30. Olimex sells an LT8912B adapter
  for €14.95. No HDMI audio documented.
- USB 2.0 HS OTG host on the chip → USB MSC stick is possible.
- M5Stack options: Stamp-P4 (P4NRW32, 16 MB flash, 32 MB octal PSRAM, USB HS
  OTG, DSI 2-lane, no HDMI); Unit PoE-P4 + Add-on Display Out (LT8912B +
  USB-A). (Later confirmed on the bench: Unit PoE-P4, ESP32-P4 rev v1.3.)

Budget (plan around, verify by experiment 01):
| Item | Estimate |
|---|---|
| Frame buffer 1920×1088 RGB565 | ~4.2 MB; 3 buffers fit in 32 MB PSRAM |
| Decode write + DSI read at 30 fps, RGB565 | ~250 MB/s of ~400 MB/s PSRAM |
| MJPEG 1080p30 at 150–250 KB/frame | 4.5–7.5 MB/s from USB |
| DSI 2-lane | 1080p30 RGB888 ≈ 1.5 Gb/s, within 2-lane budget |

Why P4 fits the requirements: no OS, firmware in flash, stick mounted
read-only → nothing to corrupt on power loss; the loop is our own code, so
the next loop's first frame can be decoded before the last one ends.

## Non-Raspberry-Pi SBCs
- Libre Computer Le Potato (Amlogic S905X, 2017): $30–35, full HDMI, 4K
  decode. Not chosen: 2017 SoC.
- Radxa ROCK 4D (RK3576, 2025): full-size HDMI 2.1 (docs say 4K120; product
  brief says 8K60 — conflicting, irrelevant for 1080p), H.264/H.265/VP9/AV1
  decode, PoE option, launch price ~$30 for 2 GB; 4 GB $59.99 (Amazon 3rd
  party, Jan 2026). Current 2 GB price not found.
  - Mainline Linux: VDPU381/VDPU383 decoders (RK3588/RK3576) merged, announced
    by Collabora Feb 2026. Known issue June 2026: RK3576 H.264 de-blocking
    artefacts on mainline (BSP warm-up step missing), throughput below BSP;
    HEVC correct.
  - LibreELEC 13 test images cover RK3576; a tester ran ROCK 4D and called
    it a likely sweet spot. Sept 2026 images: Linux 7.2.1 + Kodi 22 beta2.
    No 10-bit profile 2 yet; no YUV422 in DRM on RK3588/RK3576.
  - Vendor Radxa OS (Rockchip 6.1 BSP + MPP) is the most mature decode path.
- Rikomagic DS08 (RK3588, Android signage box): dual HDMI, 8K H.265; costlier
  and closed.

Trade-off against P4: SBC wins on codec freedom (any MP4, up to 4K, full
HDMI, no transcode) and development effort; loses on boot time (10–30 s
typical for Linux) and needs a read-only root (LibreELEC's squashfs system
partition gives that by default).

## Update (same day): SBC re-selection
The ROCK 4D was dropped (AI-oriented SoC, standard-Pi size); the target became
a board smaller than a standard Pi, without requiring full-size HDMI.
Outcome: **Orange Pi Zero 3 1GB (H618)**, 50x55 mm, micro-HDMI (4K60),
Gigabit Ethernet, 5 V 3 A USB-C.

Considered and not chosen: Radxa ROCK 2F (RK3528A, TV-box chip, out of
stock), NanoPi Zero2 (RK3528A, no HDMI), Radxa ZERO 3W/3E (RK3566, mostly
out of stock), Orange Pi Zero 2W (same H618, no Ethernet, later delivery),
Orange Pi Zero 3W / Zero 4 (A733, video support unknown).

### H618 hardware decode on Linux (checked after the choice)
An earlier assumption was that Allwinner's decode drivers are mature in
mainline. The sources found do not support that for H618:
- Mainline Cedrus (stateless V4L2) does H.264 and partial HEVC on older
  Allwinner SoCs (Pine64 wiki; Phoronix, HEVC from Linux 5.5). An Armbian
  thread says H616 support would still need to be added to Cedrus; no source
  confirms it landed.
- LibreELEC: no official H618 image; chewitt (Oct 2023) says upstream kernel
  and U-Boot support must come first and the project will not use vendor
  sources. jernej published H616/H618 test images (Feb 2024): Zero 3 "works
  fine though (without the audio)", images "not stable yet", HEVC artefacts
  with an AFBC workaround. Newest related report: May 2025, unclear whether
  decode was hardware.
- Armbian forum: mixed Zero 3 reports (one with working H.264 hwdec under
  Bookworm, others without). Armbian forum threads were reviewed only
  through search-result summaries.
- Orange Pi vendor Linux images: no information found.
So an SBC player would start by finding a stack that decodes in hardware.
